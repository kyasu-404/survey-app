# Миграции БД

Production-изменения БД хранятся здесь как SQL-файлы с датой в имени.

Правила:

- не редактируйте миграцию после применения в shared-окружении;
- проверяйте миграции на staging-копии production-данных перед production;
- оборачивайте schema-изменения в `begin;` / `commit;`, если команды поддерживают транзакции;
- не используйте `DROP TABLE`, `DROP SCHEMA`, `TRUNCATE` или широкий `DELETE FROM` без описанного бэкапа и плана отката.

После массовых импортов, восстановления дампа или резкого роста `forms`/`responses` проверьте планы запросов и свежесть статистики PostgreSQL. `planned` counts и выбор индексов опираются на статистику `ANALYZE`; если оценки стали явно кривыми или поиск/пагинация внезапно замедлились, сначала проверьте `ANALYZE public.forms;` и `ANALYZE public.responses;` на staging-копии, затем применяйте в production в безопасное окно.

Cursor/keyset pagination пока не является миграционной задачей. Текущие списки используют стабильный порядок `created_at desc, id desc`; переход к cursor pagination стоит планировать только при глубоких прокрутках или заметной стоимости `OFFSET`.

`202609081200_forms_keyset_pagination.sql` добавляет RPC `list_forms_keyset` с правами вызывающего пользователя.
Применяется перед frontend с cursor pagination; использует существующие индексы и RLS.
Выполняет `NOTIFY pgrst` для обновления схемы без перезапуска.

`202609091200_employee_form_access.sql` отделяет блокировку аккаунта от доступности его форм.
Все активные сотрудники получают чтение форм и ответов друг друга, включая закрытые формы и
вложения сохранённых ответов. Права на изменение и удаление не расширяются. Таблицы и колонки
не меняются; frontend пересобирать не требуется.

Поведенческая проверка для этой миграции: `database/employee_access.test.sql`. Запускайте её после
миграции только на отдельной базе с именем `survey_access_check_*` и копией production-данных.
Проверка создаёт временные тестовые записи внутри транзакции и завершает её `rollback`.
