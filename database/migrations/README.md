# Миграции БД

Production-изменения БД хранятся здесь как SQL-файлы с датой в имени.

`202611182030_response_upload_size.sql` повышает максимальный размер одного файла
ответа до 50 МиБ (52428800 байт). Миграция обновляет bucket `survey-files`,
резервации и политики Storage. Она сохраняет суммарные квоты и существующие вложения.

Перед публикацией frontend примените миграцию ролью с правами владельцев
функций и политик, обновите Edge Function `form-admin` и задайте для контейнера
Storage `FILE_SIZE_LIMIT` не ниже 52428800. Для маршрутов загрузки с префиксом
`/api/storage/v1/object/survey-files/` и на отдельном API-хосте
`/storage/v1/object/survey-files/` нужен `client_max_body_size` не ниже `55m`,
чтобы запрос в формате multipart вмещал файл в 50 МиБ. Для версий
self-hosted Compose, где значение задано прямо в `services.storage.environment`,
обновите его там и пересоздайте только контейнер Storage.

`202611131200_smtp_certificate_policy.sql` добавляет в `mail_settings` флаг
`allow_invalid_certificate` (`boolean not null default false`). Применяется перед
обновлением `mail-admin` и `mail-worker`; существующие SMTP-настройки и пароль
сохраняются. Проверка сертификатов остаётся включённой, пока администратор явно
не сохранит исключение. Для отката достаточно вернуть прежние worker, Edge
Function и frontend, оставив добавленную колонку в БД.

`202611101200_review_corrections.sql` применяется после предыдущих миграций и до
обновления `form-admin`, `user-admin` и frontend. Добавляет сервисные RPC атомарного
удаления формы вместе с заявками на удаление всех вложений и атомарной блокировки
сотрудника в `profiles` и `auth.users.banned_until`. Последний повторяет запись
бан-поля GoTrue, сохраняя существующий срок 876000 часов; конкурирующие операции
сериализуются блокировкой строки. Не изменяет пароли, роли, токены или схемы форм.
Фильтры и статистика активности учитывают лимит ответов; `list_forms_by_activity`
применяет тот же критерий до LIMIT, сохраняя RLS вызывающего пользователя.

Проверка: `SURVEY_TEST_DATABASE_URL=... node --test database/integration.test.mjs`
создаёт только изолированные `survey_personal_check_*` базы. Включает bootstrap,
обновление прежней схемы, 1025 вложений, гонку удаления с редактированием ответа,
откат блокировки при ошибке профиля и одновременные блокировки/разблокировки.
Очередь удаления Office сохраняет прежнюю задержку, необходимую для выданных ссылок.
Для отката верните прежние версии Edge Functions и frontend, оставив новые функции
БД: миграция не переписывает существующие данные. Боевые миграции требуют бэкапа
и предварительной проверки на staging-копии, согласно правилам ниже.

`202610281300_remove_legacy_mail_rpcs.sql` удаляет неиспользуемые
`enqueue_mail_reminder_batch`, `list_missing_form_organizations` и
`list_missing_form_organizations_snapshot`. Текущая рассылка использует
`prepare_form_mail_recipients` и `enqueue_form_mail_batch`. Миграция применяется
после всех предыдущих, не меняет данные и не использует `CASCADE`.
Проверка bootstrap и миграции, ограничения и порядок отката описаны в
[отчёте по архитектуре](../../docs/review-architecture-2026-10-28.md).

Правила:

- не редактируйте миграцию после применения в shared-окружении;
- проверяйте миграции на staging-копии production-данных перед production;
- оборачивайте schema-изменения в `begin;` / `commit;`, если команды поддерживают транзакции;
- не используйте `DROP TABLE`, `DROP SCHEMA`, `TRUNCATE` или широкий `DELETE FROM` без описанного бэкапа и плана отката.

После массовых импортов, восстановления дампа или резкого роста `forms`/`responses` проверьте планы запросов и свежесть статистики PostgreSQL. `planned` counts и выбор индексов опираются на статистику `ANALYZE`; если оценки стали явно кривыми или поиск/пагинация внезапно замедлились, сначала проверьте `ANALYZE public.forms;` и `ANALYZE public.responses;` на staging-копии, затем применяйте в production в безопасное окно.

Cursor/keyset pagination пока не является миграционной задачей. Текущие списки используют стабильный порядок `created_at desc, id desc`; переход к cursor pagination стоит планировать только при глубоких прокрутках или заметной стоимости `OFFSET`.

`202609081200_forms_keyset_pagination.sql` добавляет RPC `list_forms_keyset` с правами вызывающего пользователя.
Применяется перед frontend с cursor pagination; использует существующие индексы и RLS.
Выполняет `NOTIFY pgrst` для обновления схемы без перезапуска.

`202609091200_employee_form_access.sql` отделяет блокировку аккаунта от доступности его форм.
Все активные сотрудники получают чтение форм и ответов друг друга, включая закрытые формы и
вложения сохранённых ответов. Права на изменение и удаление не расширяются. Таблицы и колонки
не меняются; frontend пересобирать не требуется.

Поведенческая проверка для этой миграции: `database/employee_access.test.sql`. Запускайте её после
миграции только на отдельной базе с именем `survey_access_check_*` и копией production-данных.
Проверка создаёт временные тестовые записи внутри транзакции и завершает её `rollback`.

`202609160200_organization_archive.sql` добавляет `is_archived` с исходным значением `false`.
Триггер превращает DELETE организаций в архивирование, сохраняя UUID и связанные данные.
Публичный список и список несдавших исключают архив; отдельный RPC выдаёт названия архивных
ОУ из сохранённых ответов сотрудникам или владельцу browser capability без передачи email.
Триггер ответов разрешает архивную ОУ только при сохранении прежнего значения в том же поле
того же ответа. Импорт frontend явно передаёт `is_archived: false` для восстановления.

Применять перед обновлением frontend, после бэкапа и проверки на копии production.
Проверка: `database/organization_archive.test.sql` на базе `survey_archive_check_*`.
Скрипт откатывает все тестовые записи. Миграция не меняет существующие UUID или ответы.
При откате frontend оставьте аддитивную миграцию и архивные записи: удаление колонки или
отключение триггера снова допустит потерю связей. Полный бэкап нужен для аварийного восстановления.

`202609160300_forms_table_sort.sql` добавляет RPC `list_forms_sorted` и индексы для названия,
автора и числа ответов. RPC работает с правами вызывающего пользователя, соблюдает RLS,
применяет все общие фильтры до серверной сортировки и LIMIT, возвращает дополнительную строку
для проверки следующей страницы. Динамический SQL использует только разрешённые выражения
и направления; все значения фильтров и курсора передаются параметрами. Старый RPC не меняется.

Перед frontend примените миграцию на staging-копии и запустите `database/forms_table_sort.test.sql`
на базе `survey_sort_check_*`. Проверка проходит все шесть колонок в обоих направлениях на 67
строках, одинаковые ключи, фильтры, точность дат, вставку перед курсором и права доступа;
тестовые записи откатываются. Для отката интерфейса можно вернуть предыдущую сборку,
оставив аддитивную миграцию: данные форм и ответов она не меняет.

`202609291800_personal_form_links.sql` добавляет постоянные ссылки организаций,
проверку привязки ответа и подготовку приглашений/напоминаний для SMTP worker.
Применяется перед обновлением `mail-admin`, `form-admin` и frontend.
Проверка: `database/personal_links.test.sql` на изолированной `survey_personal_check_*`.
Подробности, поведение переключателя и откат: [docs/personal-links.md](../../docs/personal-links.md).


`202609292300_site_settings_author_access.sql` добавляет список сайтов iframe, публичный
RPC заголовка CSP, метаданные favicon и отдельный bucket `app-favicons` (запись только
через серверную проверку). Управление персональными ссылками и рассылкой, включая
чтение истории, ограничено автором формы. Администратор чужой формы не имеет исключения.
После миграции разверните `functions/app-settings` и динамическую политику nginx по
`docs/site-settings.md`. Начальный список сайтов пуст: встраивание запрещено.

`202610050900_nested_personal_organizations.sql` проверяет привязанную организацию
в каждой записи динамических панелей, включая вложенные панели и `valueName`.
Напоминания используют тот же обход, чтобы исключать уже ответившие организации.
Применяется перед обновлением frontend. Проверки: `database/personal_links.test.sql`
и `database/tests/nested_personal_organizations.sql` на изолированной
`survey_personal_check_*`; тестовые записи откатываются.

`202610270900_response_scope_validation.sql` проверяет ключи ответа в их реальных
областях данных, включая каждую запись `paneldynamic`, вложенные панели, `valueName`
и комментарии SurveyJS. Все присутствующие организации проходят проверку UUID,
справочника и разрешённого типа; триггер блокирует их `FOR SHARE` и разрешает архив
только по прежнему пути (включая индекс записи) в том же ответе. RPC сохранённых
организаций использует тот же обход, сохраняя ограничения доступа к истории.
Существующие ответы миграция не переписывает. Старые некорректные данные будут
отклонены при следующем сохранении; на staging проверьте их до production.

Проверки: `database/tests/response_scope_validation.sql`,
`database/tests/response_comments.sql`, `database/tests/nested_personal_organizations.sql`
и `database/personal_links.test.sql` на изолированной `survey_personal_check_*`,
а также `database/organization_archive.test.sql` на `survey_archive_check_*`.
После миграции обновите `form-admin`, `user-admin`, `mail-admin`, `app-settings`
и frontend: удаление публичного вложения теперь требует `browserId` владельца
резервации. Файлы, отсоединённые на другом устройстве, очищаются штатной уборкой.

`202610281200_code_review_fixes.sql` согласует фильтр и сортировку статуса с дедлайном,
экранирует `%`, `_` и `\` в поиске форм и возвращает актуальное право редактирования
после закрытия формы последним ответом. Истечение дедлайна само по себе не переписывает
`is_public`: активность определяется вместе со сроком; будущий срок не открывает закрытую форму.
Добавляет `survey_upload_reservations.cleanup_claimed_at`: повторная выдача просроченной
резервации допускается через 10 минут после неудачной/прерванной очистки. Старые claims
без времени можно повторить сразу. `office_documents.last_save_error_at` позволяет отличать
старую ошибку автосохранения от новой, даже если сообщения совпадают.

Перед обновлением frontend и Office service примените миграцию на отдельной копии БД,
выполните `database/tests/code_review_fixes.sql` на `survey_personal_check_*` и
`database/forms_table_sort.test.sql` на `survey_sort_check_*`, затем примените её в production
по принятой процедуре выпуска. Права на рассылки и персональные ссылки не расширяются.
При откате приложений можно оставить аддитивную миграцию и новые колонки.

`202610281600_response_attachment_ownership.sql` проверяет принадлежность новых
вложений в общем триггере ответов. Для `public/` обязательна действующая резервация
браузера; файлы сотрудника проверяются по его `auth.uid()`. Ранее прикреплённые
файлы того же ответа сохраняются при редактировании, даже после удаления старой
резервации. Блокировка строки резервации сохраняет защиту от гонки с очисткой.

Для персональных ссылок добавлены `response_browser_hash` и служебные RPC
`reserve_personal_survey_upload` / `bind_personal_survey_upload`. Они сохраняют
локальный browser capability для черновиков и отдельно привязывают загрузку к
персональному ответу. Старый черновик получает привязку при восстановлении и перед
отправкой после проверки браузера и токена, даже если предпросмотр отключён.
Обновление требует согласованного выпуска миграции,
`form-admin` и frontend; открытые персональные формы следует перезагрузить.
Сначала примените миграцию, затем опубликуйте Edge Function и frontend.

Также обход схемы безопасно обрабатывает JSON `null` и другие значения, не
являющиеся массивами, в `pages`, `elements` и `templateElements`.
Проверки: `database/tests/response_attachment_ownership.sql` и
`database/tests/response_scope_validation.sql` на изолированной
`survey_personal_check_*`; все тестовые данные откатываются.

`202610291200_final_review_fixes.sql` закрывает замечания финального review:
проверяет типы ответов, нормализует файловые значения (включая Storage URL),
согласует прикрепление и удаление через общую блокировку объекта и постоянный
признак удаления. Служебный `delete_form_responses_with_files` принимает решение
по полному набору ссылок внутри БД, без ограничения строк PostgREST. Сохранённый
ответ позволяет исходному браузеру восстановить файл после удаления резервации.
Также отзываются исторические column INSERT grants на `responses`.

Это аддитивная миграция для существующей БД; bootstrap повторно не применять.
Перед выпуском проверьте владельцев заменяемых функций и таблицы `responses`:
нужна роль с правами владельца этих объектов (в штатной установке — `postgres`).
Сначала примените миграцию, затем согласованно обновите `form-admin`, frontend и
Office service. Редактор передаёт обязательную `expectedRevision`; старые вкладки
после обновления должны перезагрузиться. Старый локальный черновик без revision
сохраняется для копирования/сохранения шаблоном и не перезаписывает текущую форму.

Deletion claims не истекают автоматически: поздно завершившийся запрос Storage
не должен удалить заново прикреплённый файл. Повторное удаление того же пути
допустимо; для новой загрузки создаётся новый путь. При откате приложения новые
DB-защиты лучше оставить; откат на старый Edge-код требует отдельной проверки
совместимости с обязательной версией редактора и файловыми значениями.

Проверки: `SURVEY_TEST_DATABASE_URL=... node --test database/integration.test.mjs`
после установки зависимостей `office-service`. Нужны PostgreSQL с правом создавать
изолированные базы и `psql`. Runner создаёт/удаляет только собственные
`survey_personal_check_*`; рабочую схему не изменяет. Он проверяет bootstrap,
аддитивную миграцию с существующей формой, SQL-регрессии и две конкурирующие
транзакции attach/delete. Для проверки обновления конкретного старого baseline
можно передать `SURVEY_TEST_PREVIOUS_SCHEMA=/absolute/path/schema.sql`.

`SURVEY_TEST_SCALE=1` дополнительно запускает тяжёлую legacy-проверку лимита
экспорта на 10001 ответе; обычный прогон проверяет новые границы безопасности и
конкуренцию без этого массового наполнения.

`202611221200_automations_notifications.sql` добавляет персональные уведомления, правила,
журнал срабатываний и переходы от событий форм к существующей почтовой очереди. Записи
уведомлений подключаются к публикации `supabase_realtime`. Операции воркера доступны
только `service_role`. Для ссылок в письмах передайте действующий `PUBLIC_APP_URL`
в окружение `mail-worker`.

Порядок выпуска — миграция, пересборка и запуск почтового воркера, публикация frontend.
Для проверки используйте `database/integration.test.mjs` с изолированным PostgreSQL.
Скрипт проверяет новую БД и обновление предыдущей схемы, запускает
`database/tests/automations.sql` и `database/tests/automation_regressions.sql`, затем удаляет тестовые базы.

`202611221300_announcements.sql` добавляет объявления администрации после
`202611221200_automations_notifications.sql`. Расписание и доступная аудитория
вычисляются в БД при чтении. Состояние просмотра, прочтения и подтверждения хранится
отдельно для каждого пользователя. Проверка свежей схемы и обновления выполняется
через `database/integration.test.mjs` и включает `database/tests/announcements.sql`.
Миграцию применяют перед обновлением frontend.

`202611221400_automation_review_fixes.sql` отделяет очередь автоматизаций от
приглашений, напоминаний и переключения персональных ссылок, ограничивает
отправку и маскирует вложения в тексте писем. Адресат из ответа выбирается только
из справочника организаций по полю вне повторяющейся панели и получает краткое
письмо. Лимиты составляют 50 правил на владельца, 500 получателей автоматизаций
на владельца за час UTC и от 15 минут между периодическими запусками.

Перед применением остановите mail-worker штатно, чтобы завершить уже начатые
отправки. Миграция отключает активные правила с несовместимым адресатом, форматом
динамического письма или интервалом. Она отменяет ещё не взятые воркером письма
автоматизаций из прежней очереди, поскольку после постановки в очередь нельзя
восстановить параметры формирования письма. Обычные рассылки и зафиксированные
результаты отправок сохраняются. Тесты `database/tests/automation_review_fixes.sql`
и проверка обновления заполненной очереди запускаются из `database/integration.test.mjs`.

`202611221410_announcement_review_fixes.sql` уточняет проверку ссылок и блокирует
перенос даты уже действующей публикации и изменение срока архивного объявления.

`202611231200_review_followup.sql` проверяет, что значения сравнений содержат
значимый текст, убирает пробелы и переводы строк по краям описаний правил
и отклоняет ссылки и адрес приложения с явно указанным портом 0.
После применения миграций обновите frontend и запустите обновлённый mail-worker.

`202611231300_notification_center_delivery_events.sql` сохраняет срабатывания и итог отправки в истории правила.
Ранее созданные служебные уведомления исключаются из личной ленты и счётчика.
Миграция убирает устаревшие категории из сохранённых настроек, сохраняя выбор
для остальных событий. Примените миграцию перед обновлением frontend.

`202611231400_default_response_notification_opt_in.sql` отключает уведомления
о новых ответах для всех учётных записей, в том числе созданных после обновления.
Пользователи могут снова включить их переключателем «Новые ответы» в настройках
уведомлений. Уведомления, полученные ранее, и настройки остальных событий сохраняются.
Примените миграцию после `202611231300_notification_center_delivery_events.sql`
и перед обновлением frontend.

`202611231500_review_regressions.sql` учитывает лимит попыток при повторном захвате
приглашений и напоминаний. Просроченные задания с исчерпанными попытками переводятся
в ошибку при опросе очереди. Изменение получателей, формата или текста письма
отменяет ещё не взятые в отправку письма и ожидающие запуски с прежними настройками.
Архивирование выключает правило и освобождает место в лимите из 50 правил.
История запусков и завершённых отправок доступна в архиве. При следующей
проверке порога счётчики с условиями равенства пересчитываются порциями.
Проверки входят в `database/integration.test.mjs` и `database/tests/review_regressions.sql`.

`202611231600_form_closed_automation.sql` добавляет для общих автоматизаций событие
завершения сбора ответов. Закрытие вручную, достижение лимита и истечение срока
ставят письмо в существующую очередь. Правило действует с момента включения.
После повторного открытия формы следующее завершение сбора запускает правило снова.
Примените миграцию перед обновлением frontend.

`202611232200_full_code_review_fixes.sql` закрывает замечания полного технического аудита:
устраняет обход wildcard MIME и загрузки в формы без файловых вопросов (включая `signaturepad`
и legacy-контейнеры), исправляет проверку владельца формы в `can_manage_survey_asset` и
очистку осиротевших фонов/фавиконов, блокирует ведущие управляющие символы и CSS-экранирование
в схемах/темах, добавляет проверку строк и ключей `matrixdynamic`/`matrixdropdown`, закрывает
TOCTOU в `delete_form_responses_with_files`, оптимизирует `prepare_form_mail_recipients` и
`list_saved_form_organizations`, добавляет недостающие индексы (и удаляет дублирующие),
удаляет устаревшие `SECURITY DEFINER`-функции и отзывает лишние права `anon`/`authenticated`
на `responses`, исключает шаблоны из публичных RPC, добавляет сериализованные RPC управления
ролями/удалением сотрудников (`set_employee_role`, `assert_can_delete_employee`) с защитой
последнего активного администратора, а также создаёт выделенную роль БД `office_service`
с минимальными привилегиями (после миграции для перевода `office-service` задайте роли пароль:
`ALTER ROLE office_service WITH LOGIN PASSWORD '...';`).
Применяйте с `lock_timeout` перед обновлением Edge Functions, `mail-worker`, `office-service` и frontend.

После неё примените **202611232230_review_followup.sql**. Миграция объединяет
проверку прав и удаление сотрудника в одной транзакции, уточняет валидацию ответов
в старых схемах и по фиксированным строкам матрицы и защищает шаблоны от загрузки
файлов ответов. Для изображений оформления действует лимит 500 объектов на автора,
включая несохранённые формы. Пользовательские изображения галереи существующей формы
хранятся до ручного удаления. Автоматически удаляются неиспользуемые копии,
отмеченные при переносе между формами. Воркер очищает старые отметки удаления
только для отсутствующих файлов без действующих записей резервирования.

При обновлении сначала примените миграцию, затем пересоздайте Edge Functions
и обновите почтовый воркер. Старому user-admin понадобится обновление для удаления
сотрудников. Рабочие темы с управляемыми изображениями хранят ссылку на Storage
в виде токена. Уже записанные темы хранятся
без изменений. Новый фильтр применяется при создании или изменении темы,
поэтому старые формы продолжают принимать ответы.
