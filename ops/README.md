# Эксплуатация forms.imc-mosk.ru

Изменения от 21 сентября 2026 года. Backend: STSS, `/opt/survey-app`; frontend: MAGI, `/var/www/forms.imc-mosk.ru/dist`.

## Резервные копии

Копии находятся **на STSS** в `/mnt/data/forms_backup/`, на отдельном RAID. Каталог и файлы доступны только root: архив содержит ключи, пароли и пользовательские данные. Скрипт отказывается работать, если `/mnt/data` не смонтирован. RAID защищает от отказа диска, но не заменяет независимую копию вне сервера.

- `forms-backup.timer`: ежедневно в 03:15 по времени STSS, случайная задержка до 5 минут; сохраняются последние 5 завершённых полных копий (включая ручные). Плановые сервисы ждут освобождения общей блокировки до двух часов.
- `forms-backup-verify.timer`: по воскресеньям в 04:30, задержка до 5 минут; восстановление последней копии в отдельный временный PostgreSQL без сети и опубликованных портов.
- Каталоги имеют вид `YYYY-MM-DD/HH-MM-SS-full` или `YYYY-MM-DD/HH-MM-SS-deploy-название`, время московское. `.partial-*` означает незавершённую копию; такие каталоги учитываются отдельно. Перед новой попыткой скрипт удаляет старые незавершённые копии, сохраняя до двух последних попыток. Для архивов публикаций действует отдельный лимит 5. Старейшие удаляются, пустые папки дат убираются. Прежние имена с UTC поддерживаются при поиске; `--organize` проверяет и переносит их в новую структуру.

Описание файлов и восстановления находится в [BACKUP_FILES.md](BACKUP_FILES.md); скрипт автоматически кладёт его в корень хранилища как `README.md`.

Содержимое: `postgres.dump`, `supabase-internal.dump`, `globals.sql`, versioned Storage, `configuration.tar.gz` с исходниками, действующим Compose, окружением, Edge Functions и контекстом сборки mail-worker, `db-config` с конфигурацией PostgreSQL и ключом шифрования, `manifest.json` с SHA-256 и перечнем Storage-объектов. Сборка frontend на STSS синхронизируется с MAGI при публикации и входит в архив конфигурации. Активные конфигурации nginx MAGI и прежняя сборка дополнительно находятся в архиве соответствующей публикации `YYYY-MM-DD/HH-MM-SS-deploy-*/magi-before.tar.gz`.

Основная база и перечень объектов Storage читаются из одного PostgreSQL snapshot. Storage копируется до и после выгрузки; отсутствующая версия или неверный размер останавливают копирование. Повторные копии неизменённых файлов используют hard links; **не редактируйте файлы внутри готовых копий**. SHA-256 проверяется до объявления копии завершённой. `restore-check.json` появляется только после успешного восстановления обеих баз и сверки Storage.

Команды на STSS:

```sh
sudo systemctl list-timers forms-backup.timer forms-backup-verify.timer
sudo systemctl start forms-backup.service
sudo systemctl start forms-backup-verify.service
sudo journalctl -u forms-backup.service -u forms-backup-verify.service --since yesterday
sudo python3 /opt/survey-app/ops/backup-forms.py --verify /mnt/data/forms_backup/YYYY-MM-DD/HH-MM-SS-full
sudo python3 /opt/survey-app/ops/backup-forms.py --restore-check /mnt/data/forms_backup/YYYY-MM-DD/HH-MM-SS-full
sudo python3 /opt/survey-app/ops/backup-forms.py --organize
```

Проверка восстановления выполняется отдельно от рабочей БД. Проверка и создание копий выполняются последовательно под общей блокировкой. Она использует тот же Docker image ID PostgreSQL, что указан в manifest; не удаляйте этот образ, пока на него ссылаются нужные копии. При переносе на другой сервер понадобится соответствующий образ Supabase PostgreSQL. Проверка восстанавливает данные и схему без владельцев и ACL; это не имитация полного аварийного переключения приложения.

Для аварийного восстановления сначала разверните отдельный стенд с тем же compose и образом PostgreSQL, сохраните текущую рабочую систему, проверьте архив и подготовьте роли из `globals.sql`. Восстановите обе БД с правильными владельцами/правами, конфигурацию/ключи и Storage в соответствующие volume. Проверьте вход, чтение/сохранение формы, отправку ответа, скачивание вложений, обработку Office/почты. Только после проверки переключайте трафик. Изолированный стенд не должен отправлять реальные письма или запускать рабочие фоновые задания. TLS-сертификаты, ОС, Nextcloud и другие приложения не входят в этот набор копий.

## Сеть

`forms-ingress.service` ограничивает доступ к сервисным портам на всех входящих
интерфейсах STSS, кроме loopback. API 8000/8443 и Office 8095 доступны по IPv4
только MAGI `192.168.6.99`. PostgreSQL 5432 и pooler 6543 закрыты извне.
Укажите `SURVEY_FRONTEND_IP`, чтобы сменить IPv4 MAGI. При необходимости разрешите
точный IPv6 MAGI через `SURVEY_FRONTEND_IPV6` и задайте список интерфейсов через пробел
в `SURVEY_INGRESS_INTERFACES`. Скрипт атомарно обновляет цепочки приложения в каждой
семье IP, включая IPv6 INPUT даже при отсутствии IPv6 DOCKER-USER. Обновляйте
через `systemctl reload forms-ingress.service`. Удаление правил выполняется явной
командой `sudo /opt/survey-app/ops/forms-ingress.sh --remove`.

Держите host-bind шлюза и Office на частном адресе backend, доступном MAGI.
При развёртывании через Docker с iptables проверьте наличие цепочки `DOCKER-USER`
для опубликованных портов. Прямое подключение к БД для обслуживания возможно
локально через `docker exec`.

На обоих vhost MAGI nginx перезаписывает `X-Survey-Client-IP` и `X-Forwarded-For` значением `$remote_addr`; Edge Function использует этот заголовок для бюджета загрузок. Если перед nginx появится ещё один proxy, сначала настройте real_ip только для доверенных адресов, затем проверьте лимиты. Не принимайте этот заголовок напрямую от клиента.

Кандидаты для обоих vhost готовит `ops/prepare-magi-nginx.py`. Команда создаёт
общие директивы уровня `http` и два набора правил для существующих HTTPS-блоков.
Задайте адреса STSS, доступные MAGI, например:

```sh
python3 ops/prepare-magi-nginx.py --backend 192.168.6.80:8000 \
  --office 192.168.6.80:8095 --output /private/path/nginx-review
```

Объедините `survey-http.conf` с действующими общими директивами без дублей,
`forms-proxy.inc` с vhost `forms.imc-mosk.ru`, а `api-proxy.inc` с отдельным
`api.forms.imc-mosk.ru`. Сохраните настройки TLS, Studio и динамического iframe.
Используйте фиксированный канонический хост в HTTP-редиректе. Для CSP разрешите
явные origin API и Realtime и, если используется внешний сборщик ошибок,
его точный origin. Для HTTPS upstream динамической iframe-политики требуется
доверенный сертификат. Проверьте полный конфиг через `nginx -t` перед reload.

## Ограничения и масштабирование

- Ответы: страницы по 50 записей, серверный общий счётчик. Выгрузка — единый снимок, максимум 10 000 ответов/32 MiB JSON за запрос; для больших форм выбирайте нужные ответы.
- ZIP вложений передаётся потоком через Office API. Одна выгрузка на сотрудника, до двух одновременных выгрузок на сервис.
- Анонимные файлы: резервации, проверка фактического размера Storage, ограничение по форме/посетителю/сетевому адресу; просроченные незакреплённые файлы удаляет mail-worker. Посетители за одним NAT разделяют сетевой бюджет.
- Office: не больше 500 ответов на задание; до 20 заданий глобально/2 на пользователя, общий бюджет входных данных 64 MiB. Снимок задания — до 8 MiB. Durable queue хранится в PostgreSQL и переживает перезапуск.
- Один обработчик очереди Office выбирается advisory lock PostgreSQL. До 2 тяжёлых worker tasks одновременно, 4 в ожидании, 75 секунд на операцию, ограниченный heap. Добавление реплик HTTP само по себе не увеличивает число обработчиков документов. Увеличивать лимиты можно только после измерения памяти/CPU и нагрузки соседних сервисов.
- Необходимость реплик БД, шардирования очереди или серверного экспорта определяйте по метрикам. Локальный тест со 100 000 синтетических ответов не гарантирует такую же задержку на рабочем сервере.

## Публикация и откат

Перед изменениями создавайте копию на STSS и проверяйте миграции на её изолированном восстановлении. Для архива публикации получите папку командой `sudo python3 /opt/survey-app/ops/backup-forms.py --deployment-dir frontend`, сохраните туда архивы и после окончания записи вызовите `--organize`: проверка и ротация оставят 5 последних архивов публикаций. Миграции `202609202200_consistent_exports.sql`, `202609202210_upload_reservations.sql`, `202609212200_office_generation_jobs.sql` уже применены; не применяйте их повторно без проверки состояния БД.

Frontend собирается Node 22 с production `VITE_*`. Загружайте файлы сборки на MAGI сначала, затем атомарно заменяйте `dist/index.html`. Старые assets сохраняются для открытых вкладок. Сохраните предыдущие образы или исходники сервисов и конфигурации proxy. Для отката frontend верните прежний index и assets из `YYYY-MM-DD/HH-MM-SS-deploy-*/magi-before.tar.gz`. Проверьте совместимость старых версий с новой схемой на стенде. Если нужен откат данных, согласуйте восстановление и перенос записей, принятых после создания копии.

Исходники, копии конфигурации и текущую сборку frontend синхронизируйте на STSS перед следующим ежедневным backup. Диагностика Office/mail: `docker logs survey-office`, `docker logs survey-mail-worker`; состояние резервного копирования — systemd/journal, успешная проверка — `restore-check.json`.
