# Резервные копии приложения «Формы ИМЦ»

Каталог на STSS: `/mnt/data/forms_backup/`. Доступ — через `sudo`: архивы содержат пользовательские данные, пароли и ключи. Не публикуйте их в Git или на сайте.

## Папки и сроки хранения

```text
forms_backup/
  README.md
  .lock
  2026-09-22/
    03-16-28-full/
    10-57-54-deploy-ui/
    11-40-00-deploy-backup-policy/
```

Название верхней папки — дата создания, следующей — время и тип копии. Используется **московское время (Europe/Moscow)**; время `createdAt` внутри manifest остаётся в UTC.

- `HH-MM-SS-full` — полная копия приложения. Создаётся ежедневно в **03:15–03:20 по Москве**, а также при ручном запуске. Хранятся **5 последних завершённых полных копий**, включая ручные. Это количество копий, а не дней.
- `HH-MM-SS-deploy-*` — архив перед изменением или публикацией. Хранятся **5 последних архивов публикаций отдельно от полных копий**. Содержимое зависит от изменяемой части приложения; такой архив не заменяет полную копию БД и вложений.
- После успешной полной копии удаляются наиболее старые сверх лимита; архивы публикаций также очищаются после их проверки. Команда `--organize` проверяет существующие копии, приводит старые названия к новой структуре и применяет оба лимита. Пустые папки дат после удаления копий убираются.
- Новые копии создаются в отдельных папках, существующие не перезаписываются. `.partial-*` означает незавершённую попытку: она не считается готовой копией и автоматически не удаляется. `.lock` служит для защиты от одновременного копирования, перестановки папок и удаления проверяемой копии.
- По воскресеньям в **04:30–04:35** проверяется восстановление последней полной копии в отдельном временном контейнере. Рабочая база при этом не перезаписывается.

## Файлы полной копии

| Файл или папка | Для чего нужен |
| --- | --- |
| `postgres.dump` | Основная БД PostgreSQL: формы, ответы, пользователи Supabase/Auth, права, настройки, метаданные вложений и заданий. Архив формата `pg_dump -Fc`, читается `pg_restore`. |
| `supabase-internal.dump` | Внутренняя БД `_supabase`, необходимая службам Supabase. |
| `globals.sql` | Глобальные роли PostgreSQL и их параметры, включая секретные данные. Нужен при восстановлении ролей и владельцев на новом сервере. |
| `storage/` | Сами загруженные файлы и их версии. В БД хранятся метаданные, поэтому одного дампа БД для восстановления вложений недостаточно. |
| `configuration.tar.gz` | Исходники приложения и текущая сборка frontend, compose/env Supabase, Edge Functions, конфигурация API/pooler, скрипты эксплуатации. Содержит секреты. |
| `db-config/` | Каталог `/etc/postgresql-custom` контейнера PostgreSQL: настройки и ключ шифрования БД. В самых ранних копиях может отсутствовать. |
| `manifest.json` | Время создания, точный Docker image ID PostgreSQL, список версий Storage и контрольные суммы SHA-256. Используется для проверки комплектности и целостности. |
| `restore-check.json` | Отметка об успешной проверке восстановления этой копии и её время. Появляется после проверки, поэтому у новой копии может отсутствовать. |

Не изменяйте файлы внутри готовых копий. Неизменившиеся файлы Storage могут разделять место на диске через hard links: каждая копия читается отдельно, удаление старой не повреждает оставшиеся, но редактирование общего файла повредит несколько копий.

## Файлы архива публикации

| Файл | Назначение |
| --- | --- |
| `magi-before.tar.gz` | Сборка frontend и активные конфигурации nginx MAGI до публикации. Есть в архивах, затрагивающих frontend/nginx. |
| `stss-before.tar.gz` | Изменяемые исходники, настройки или сборка STSS до изменения. Состав зависит от публикации; это не дамп БД. |
| `deployment.json` | Метаданные публикации и контрольные суммы. Может отсутствовать, если архив был создан только перед подготовкой изменения. Старое поле `backup` может содержать имя папки до её переименования. |
| `SHA256SUMS` | Контрольные суммы файлов архива, если были записаны при его создании. Проверка: `sudo sha256sum -c SHA256SUMS` из соответствующей папки. |

## Проверка без восстановления рабочей системы

Подставьте реальную папку полной копии:

```sh
sudo python3 /opt/survey-app/ops/backup-forms.py --verify /mnt/data/forms_backup/2026-09-22/03-16-28-full
sudo python3 /opt/survey-app/ops/backup-forms.py --restore-check /mnt/data/forms_backup/2026-09-22/03-16-28-full
```

Первая команда сверяет файлы с manifest. Вторая дополнительно запускает временный PostgreSQL без сети и опубликованных портов, восстанавливает обе БД, сравнивает число объектов Storage и удаляет тестовый контейнер. Содержимое Storage сверяется по контрольным суммам. Проверка не запускает весь сайт и не подтверждает аварийное переключение всех сервисов; владельцы и ACL при тестовом восстановлении пропускаются.

Для проверки нужен Docker image, указанный в `manifest.json`. Не удаляйте его, пока нужны соответствующие копии. На другом сервере сначала подготовьте совместимый образ Supabase PostgreSQL.

## Как примерно выполняется полное восстановление

1. Выбрать подходящую полную копию и проверить её. Сохранить текущее состояние системы перед восстановлением.
2. Поднять отдельный стенд с совместимым Supabase/PostgreSQL и нужной конфигурацией. Запретить ему отправку настоящих писем и запуск рабочих фоновых заданий.
3. Разобрать `configuration.tar.gz`, восстановить настройки и секреты; вернуть `db-config`, включая ключ шифрования. Проверить пути, права и compose volumes под целевой сервер.
4. Подготовить роли из `globals.sql`, согласовав их с ролями, которые создал Supabase. Восстановить `postgres.dump` и `supabase-internal.dump` через `pg_restore`, сохранив корректных владельцев и права доступа. Не применять SQL ролей вслепую к работающему серверу.
5. Вернуть `storage/` в volume Storage того же снимка. Проверить, что версии и пути файлов совпадают с `manifest.json` и записями восстановленной БД.
6. Развернуть соответствующие Edge Functions, Office/mail-worker и frontend. Если требуется откат frontend/nginx на MAGI, использовать подходящий архив публикации; для nginx проверить `nginx -t` перед перечитыванием конфигурации.
7. Проверить вход, доступ к формам/ответам, заполнение формы, загрузку и скачивание вложений, создание документов и работу очередей. Только затем переключать рабочий трафик и включать фоновые задания.

Универсальной команды «восстановить поверх production» здесь нет: порядок зависит от того, восстанавливаются ли один компонент, база или весь сервер. Для отката только frontend обычно достаточно прежних `dist/index.html` и assets из архива публикации; это не откатывает данные БД.

Копии не включают всю ОС, TLS-сертификаты, Nextcloud и другие приложения. RAID находится на том же STSS; отдельная внешняя копия нужна для потери всего сервера.

## Обслуживание

```sh
sudo systemctl list-timers forms-backup.timer forms-backup-verify.timer
sudo systemctl start forms-backup.service
sudo systemctl start forms-backup-verify.service
sudo journalctl -u forms-backup.service -u forms-backup-verify.service --since yesterday
sudo python3 /opt/survey-app/ops/backup-forms.py --organize
```

Каталог для нового архива публикации создаётся командой `sudo python3 /opt/survey-app/ops/backup-forms.py --deployment-dir frontend`. Она выводит путь: сохраните туда нужные архивы, затем выполните `--organize` для проверки и ротации. Не запускайте организацию папок, пока в них ещё записываются архивы публикации.

Этот файл копируется из `/opt/survey-app/ops/BACKUP_FILES.md` при создании копии и при `--organize`. Скрипт и systemd-файлы входят в репозиторий, но пути, контейнер и расписание настроены под STSS; на другом сервере требуется адаптация и отдельное включение таймеров.
