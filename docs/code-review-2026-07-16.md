# Полное код-ревью Survey App — 16 июля 2026

## Итог

Проверены frontend, PostgreSQL/RLS, Supabase Storage, Edge Functions, миграции, Docker/nginx и CI. В рабочий список вошли 156 runtime/config-позиций: 153 актуальных файла и 3 удалённых дублирующих модуля. Все подтверждённые проблемы исправлены и перепроверены статическими, unit/integration и живыми HTTP/SQL-тестами.

Требуемое продуктовое поведение сохранено: активные публичные формы администратора и ответы на них по-прежнему видимы пользователям с ролью `user`. Это правило не распространяется на приватные формы, формы отключённых авторов и формы обычных пользователей без соответствующего доступа.

## Исправленные проблемы

| Область | Проблема | Исправление |
|---|---|---|
| Учётные записи | Старый JWT отключённого пользователя продолжал работать в части RLS и Edge Functions | Добавлена единая проверка `profiles.is_enabled` во все чувствительные политики и обе функции |
| Роли | Авторизация могла расходиться между UI, JWT metadata и БД | Роль берётся только из `public.profiles`; административные функции проверяют активный профиль |
| Формы | Не-администратор мог попытаться открыть в конструкторе чужую форму по ID | Добавлена проверка владельца до гидратации редактора; администратору оставлен явный доступ |
| Формы | Отключённый автор мог оставлять публичные формы читаемыми/доступными для записи | Публичность и приём ответов теперь требуют активного автора |
| Формы | Клиент мог подменять служебные поля и счётчик ответов | INSERT/UPDATE grants сведены к разрешённым столбцам; счётчик управляется только триггерами |
| Ответы | Параллельная или bulk-вставка могла превысить лимит | BEFORE-триггер атомарно резервирует слот; multi-row INSERT откатывается целиком при превышении |
| Ответы | Повтор запроса после закрытия формы мог создать дубль или показать ложную ошибку | Добавлен `submission_id`, уникальность на форму и идемпотентная обработка повторов |
| Ответы | JSON-схемы и ответы не имели достаточных серверных ограничений | Введены лимиты 256 КиБ, верхняя граница `max_responses=100000` и ограничения опасных SurveyJS URL-полей |
| Storage | Анонимные файлы можно было читать/листать | Bucket оставлен приватным; анонимам разрешена только запись в точный путь активной формы |
| Storage | Право чтения позволяло удалить чужой либо уже использованный файл | Чтение и удаление разделены; удаление требует владельца пути и отсутствие точной ссылки из ответа |
| Storage | Поиск ссылок обходил весь JSON всех ответов | Добавлена нормализованная индексированная таблица `response_file_references` и sync-триггер |
| Storage | Анонимные загрузки могли бесконтрольно накапливаться | Ограничены размер объекта (10 МиБ), число и суммарный объём на форму; добавлены точечное удаление и admin cleanup |
| SurveyJS | Схема могла инициировать внешние загрузки, небезопасную навигацию или активный HTML | Добавлены итеративный sanitizer, DOMPurify, запрет внешних media/video URL и безопасная same-origin навигация |
| Вложения | URL из сохранённого ответа мог заставить браузер обратиться к произвольному хосту | Принимаются только строгие Storage-пути либо signed URL настроенного Supabase origin/bucket |
| Кэш | Данные предыдущего пользователя могли остаться после смены сессии | Все пользовательские React Query, draft и session-кэши очищаются/разделяются по user/form |
| Пароли | Состояние страницы пользователей могло сохранять введённый пароль | Пароли исключены из session state и обнуляются сразу после операции |
| Телеметрия | Sentry tracing мог отправить query/fragment callback URL с auth-токеном | `beforeSend` и `beforeSendTransaction` удаляют credentials, query, fragment и чувствительные headers |
| Экспорт | Глубоко вложенные ответы могли вызвать рекурсивное переполнение или чрезмерную обработку | Обход сделан итеративным, с лимитами глубины/узлов и ограниченными страницами выборки |
| Supply chain | CI actions и Docker base images были привязаны к изменяемым тегам | Actions закреплены SHA, образы — digest; Node/Vite/Vitest обновлены, lockfile пересоздан |
| Docker | Публичный anon key передавался обычным build argument | Сборка использует обязательный BuildKit secret; контейнер работает non-root на 8080 |
| Ingress | Не было отдельного бюджета для массовых anonymous uploads | В production proxy добавлен лимит 1 запрос/с на IP с burst 5; Kong нельзя публиковать в обход proxy |

## Логика и надёжность

- Состояние формы закрывается ровно на последнем разрешённом ответе, без гонки счётчика.
- Повтор с тем же `submission_id` не увеличивает счётчик и считается успешным идемпотентным повтором.
- Ошибка bulk-вставки не оставляет частично записанные ответы или увеличенный счётчик.
- Просроченные и достигшие лимита формы нормализуются одинаково на сервере и в UI.
- Удаление формы идёт через Edge Function: сначала очищаются Storage-объекты, затем строка формы.
- Черновики конструктора и ответов имеют ограниченный срок жизни и отдельные ключи пользователя/формы.
- Конструктор не повторяет запрос после заведомой ошибки авторизации.
- Удалены три неиспользуемых дублирующих модуля API/login, чтобы не поддерживать расходящиеся реализации.

## Производительность

- Списки форм и шаблонов пагинируются на сервере стабильной сортировкой и используют целевые индексы.
- Dashboard stats сведены к одному агрегирующему RPC.
- Realtime-инвалидация фильтрует нерелевантные события и объединяет всплески обновлений.
- Проверка Storage-ссылок использует индекс `(object_path, form_id)`, а не JSON-скан таблицы ответов.
- Экспорт читает ответы ограниченными страницами и обходит вложенные значения без рекурсии.
- Тяжёлые SurveyJS, ExcelJS и Sentry части вынесены в отдельные chunks; установлен и проверен bundle budget.

Крупные vendor chunks SurveyJS/ExcelJS всё ещё заметны, но загружаются только на соответствующих маршрутах. Дальнейшее уменьшение возможно только через смену библиотек или более глубокую декомпозицию, что уже является продуктовым, а не локальным исправлением.

## Текущее локальное развёртывание

- Приложение: `http://localhost:3000`
- Supabase API/Kong: `http://localhost:8000`
- PostgreSQL pooler: `localhost:5432` и `localhost:6543`
- Контейнер frontend: `survey-app-frontend`, образ `survey-app-frontend:review`, restart policy `unless-stopped`

Studio внутри Supabase слушает контейнерный порт 3000, но наружу он не опубликован. Порт Windows/WSL `3000` теперь занят именно frontend-контейнером.

## Оставшиеся эксплуатационные рекомендации

Это не незакрытые ошибки в проверенном коде, а требования к реальному production-развёртыванию:

1. Не публиковать Kong/Storage напрямую; весь внешний трафик должен идти через rate-limited TLS reverse proxy.
2. Добавить CAPTCHA/Turnstile или иной abuse-control для публичных форм, если они доступны широкой аудитории. Любой полностью анонимный endpoint подвержен распределённому спаму, даже при per-IP лимите.
3. Настроить регулярный вызов admin cleanup для старых неподтверждённых загрузок и мониторинг form-wide Storage quota.
4. Хранить service-role, SMTP, database и Sentry credentials только в секрет-хранилище; ротировать после любой утечки.
5. Включить резервное копирование PostgreSQL/Storage и отдельно протестировать восстановление.
6. Перед интернет-публикацией заменить `example.com`, сертификаты и локальные upstream в корневом `nginx.conf` на реальные значения.

## Ограничения ревью

Проверялся first-party код приложения. Вендорный checkout `supabase/` рассматривался как upstream-инфраструктура: контейнеры и интеграция проверены, но полный аудит исходников самого Supabase не выполнялся. TLS, firewall, DNS, SMTP и внешнее секрет-хранилище отсутствуют в локальной WSL-среде и должны проверяться отдельно при production deployment.
