**Пагинация форм и шаблонов — 8 сентября 2026 года**

Списки переведены на cursor/keyset и установлены на `stss` и `magi`.
Кнопка «Показать ещё», фильтры, сортировка и пакетное обновление открытых карточек сохранены.

Курсор — исходные `created_at` и `id` последней показанной строки. Timestamp передаётся без
преобразования в JavaScript Date, чтобы сохранить микросекунды. Следующая страница выбирается
условием `(created_at, id) < (cursor_date, cursor_id)` и сортируется по обоим полям DESC.
Параметры курсора используются и при обновлении больше 999 открытых карточек. Первая порция
обновления начинается с начала списка; следующие продолжают её по свежим ключам.

RPC `public.list_forms_keyset(timestamptz, uuid)` возвращает только поля карточки, использует
`SECURITY INVOKER` и существующие RLS. Доступ к RPC предоставлен `authenticated` и `service_role`;
анонимный вызов запрещён. Индексы `(created_at DESC, id DESC)` и
`(author_id, created_at DESC, id DESC)` уже существовали, новые индексы не потребовались.
SQL-функция допускает inlining: имена таблиц квалифицированы, `SET search_path` отсутствует.
Фильтры, сортировка и `LIMIT` применяются PostgREST к её результату.

Для этой RPC принципиален **GET**. На установленном PostgREST 14.12 POST разбирает JSON-параметры
через `json_to_record`; проверка реального HTTP-плана показала, что условие курсора становится
`Join Filter` и предыдущие строки продолжают читаться. GET переносит сравнение пары в `Index Cond`.
Синтетический тест явно проверяет наличие этого условия в HTTP-плане и прерывается, если его нет.

Размер страницы ограничен диапазоном 1–999. Дополнительная строка определяет `hasMore`, но
не попадает в показанные карточки и курсор. Пагинация не выполняет `COUNT`; точная статистика
главной страницы по-прежнему получается отдельным существующим RPC.

| Проверка | Offset | Keyset | Ускорение |
|---|---:|---:|---:|
| Полная выгрузка 90 000 форм, порции по 20 | 161.27 с | 25.23 с | 6.39× |
| Полная выгрузка 90 000 форм, порции по 999 | 4.52 с | 1.63 с | 2.77× |
| Глубокая страница: пропущено 89 979 строк, порция 20 | 88.26 мс | 4.02 мс | 21.94× |
| Глубокая страница: пропущено 89 000 строк, порция 999 | 88.30 мс | 9.39 мс | 9.41× |
| Первая страница, 20 форм | 5.56 мс | 5.28 мс | 1.05× |

Для полных выгрузок показаны медианы трёх прогонов. Первые страницы практически не изменились;
выигрыш увеличивается с глубиной списка. На глубокой странице из 20 карточек HTTP-план offset
прочитал все 100 000 строк (90 000 прошли фильтр), выполнил сортировку и использовал 16 675
shared buffers. Keyset получил 21 строку плюс отфильтровал 2 шаблона, используя 9 shared buffers;
сравнение курсора присутствует в `Index Cond` индекса `idx_forms_created_at_id`.
Отдельное инструментальное время SQL в этих планах — 155,29 мс и 0,57 мс соответственно.
Полные планы, все прогоны и проверки сохранены в [benchmark.json](forms-keyset-2026-09-08/benchmark.json).

Набор: 100 000 искусственных форм, из них 90 000 обычных и 10 000 шаблонов; 100 профилей.
У групп из 50 строк одинаковое время создания, соседние группы отличаются микросекундой.
Таблица содержит также JSON схемы формы, который не попадает в списковую проекцию.
Таблица с индексами занимает 159 064 064 байта. Рабочие записи не копировались в тест.

Тест запускался на `stss` в отдельной временной базе того же PostgreSQL 17.6 и отдельном
контейнере PostgREST 14.12, доступном только по loopback. Использованы определения таблицы,
индексов, RLS и их вспомогательных функций из актуального baseline. Полная выгрузка выполнялась
с JWT синтетического администратора, через реальный HTTP и с получением JSON всех карточек.
У PostgREST сохранён лимит 1000 строк. Для обоих алгоритмов одинаковы проекция, фильтр исключения
шаблонов, сортировка, lookahead и размеры страниц. Offset-вариант воспроизводит прежние запросы
`GET /forms?...&offset=N&limit=pageSize+1`, keyset — новый `GET /rpc/list_forms_keyset`.

Полные выгрузки выполнены по три раза; порядок offset/keyset чередовался. Время полной выгрузки
включает передачу и разбор JSON и проверку каждой строки. Для отдельных страниц приведены
медианы десяти HTTP-чтений после двух прогревочных; получение исходной границы не входит в замер
отдельной страницы. При полной выгрузке каждый курсор берётся из предыдущего HTTP-ответа.
`EXPLAIN ANALYZE` с buffers снят отдельно, его инструментальные накладные расходы не включены
в HTTP-медианы. Это последовательный лабораторный тест на рабочем сервере, без внешней сетевой
задержки, Kong и Nginx; он не моделирует одновременную нагрузку множества пользователей.

Проверка полноты сравнивает ID **каждой** строки с эталонной последовательностью из БД и считает
SHA-256 последовательности ID. Все выгрузки содержат ровно 90 000 строк, без пропусков и дублей,
с одинаковым порядком и SHA-256 `30acfed2f40d687cc1cc036e53a8920952e7c7e529cd4d36bd18e644bf5e7815`.
При размере 20 получено 31 662 135 байт JSON за 4500 запросов; при размере 999 —
30 192 839 байт за 91 запрос. Объём внутри каждой пары алгоритмов одинаков; различие между
размерами порций объясняется повторной передачей lookahead-строк.

Дополнительно проверены шаблоны, «Мои формы», поиск по названию/автору, дата, основание формы,
обычный пользователь, заблокированный пользователь, запрет анонимного RPC и продолжение после
добавления новой формы и удаления самой строки курсора. Временные контейнер и база удалены.

Тесты приложения: 459 тестов в 61 файле, TypeScript, ESLint, 39 проверок baseline и миграций,
production-сборка и контроль размера прошли. Playwright на production-сборке проверил 200 карточек,
обновление одним GET-запросом, прокрутку и полный экспорт 200 ответов, пакетное удаление,
конструктор, публичную форму, сохранение и показ фонов. Три сценария прошли; отдельный сценарий,
требующий E2E-логина и пароля, штатно пропущен. После установки отдельно прошёл браузерный
тест страницы входа на `https://forms.imc-mosk.ru`.

На рабочем API сравнение старого списка и нового RPC выполнено для трёх существующих профилей:
девять комбинаций пользователя/фильтров и продолжение по курсору; анонимный RPC отклонён.
Рабочая таблица при проверке содержала одну форму. Эти проверки ничего не записывали в неё.
Опубликованный HTML и все шесть непосредственно подключённых assets совпали по содержимому
с проверенной сборкой. Результаты: [API](forms-keyset-2026-09-08/production-api.json),

Для повторения синтетического теста на backend-хосте с Supabase Docker:

```bash
cd /opt/survey-app
python3 ops/benchmark-forms-pagination.py \
  --rows 100000 --rounds 3 \
  --output /tmp/forms-keyset-benchmark.json
```

Скрипт сам создаёт и удаляет отдельные базу и контейнер, не добавляет формы в рабочую базу и
не меняет конфигурацию рабочего PostgREST. При обычном завершении и исключении очистка выполняется
в `finally`. Для запуска нужны Python 3, доступ к Docker и существующие контейнеры
`supabase-db`, `supabase-rest`; дополнительные Python-пакеты не нужны.

Установка уже выполнена:

- `stss`: миграция `database/migrations/202609081200_forms_keyset_pagination.sql` применена,
  кеш PostgREST обновлён через `NOTIFY`; изменённые исходники сохранены в `/opt/survey-app`.
- `magi`: production-сборка установлена в `/var/www/forms.imc-mosk.ru/dist`; HTML переключён
  атомарно после assets. Предыдущие assets с хешами сохранены для открытых вкладок.
- На обоих серверах резервные копии находятся в `/var/backups/survey-app/forms-keyset-20260908`.
  На `stss` сохранены прежняя схема `public` и изменённые исходники, на `magi` — прежний `dist`
  и отдельная копия HTML. Конфигурация Nginx прошла `nginx -t`, reload не потребовался.

Для быстрого отката фронтенда на `magi` достаточно атомарно вернуть прежний HTML — все его
assets сохранены:

```bash

sudo install -o www-data -g www-data -m 644 \
  /var/backups/survey-app/forms-keyset-20260908/index-before.html \
  /var/www/forms.imc-mosk.ru/dist/index.rollback.html
sudo mv -f /var/www/forms.imc-mosk.ru/dist/index.rollback.html \
  /var/www/forms.imc-mosk.ru/dist/index.html
```

Новый RPC можно оставить: прежний frontend с ним совместим. Не нужно восстанавливать всю схему
рабочей БД или удалять данные. Исходники при необходимости восстанавливаются из
`/var/backups/survey-app/forms-keyset-20260908/source-before.tar.gz` на `stss`.

Cursor pagination не создаёт общей snapshot между запросами: новые записи выше курсора появляются
при обновлении, а изменение полей фильтра или прав доступа может менять состав последующих
страниц. Выигрыш зависит также от фильтров и RLS: сильно избирательный фильтр может потребовать
просмотра дополнительных строк после курсора. На маленьком списке большой разницы ожидать не следует.

Технические основания: [PostgREST — inlining табличных RPC](https://postgrest.org/en/latest/references/api/functions.html),
[PostgreSQL — сравнение строк](https://www.postgresql.org/docs/17/functions-comparisons.html).
