# Исправления по дополнительному review — 2026-11-11

Выбранные пользователем ограничения: firewall не менять; внешние бэкапы не делать; публичные формы открывать только по известной ссылке без данных автора; ограничения вложений брать только из настройки вопроса автора. Совместные права сотрудников сохранены.

## Изменения

- Worker отдельно повторяет подтверждение результата в БД, не отправляя заново принятое SMTP-сервером письмо. Ошибка одного задания не переотправляет пакет. Неопределённые подтверждения видны в health; удалённое вместе с формой задание освобождает очередь.
- Обновление responses_count не запускает сравнение полных JSON-строк формы триггером ревизии. Изменения схемы, настроек и автоматическое закрытие по лимиту сохраняют revision. Порядок блокировок forms/files сохранён.
- Страница ответов применяет счётчик из Realtime без SELECT полной формы при неизменной revision; при неполных/неоднозначных событиях перечитывает авторитетное состояние.
- get_public_form(uuid) возвращает активную форму без author_id/author_name. Anon лишён табличного и старого колоночного SELECT, anonymous RLS policy удалена. Прежние ссылки продолжают работать через новый RPC.
- Вложения проверяются по сохранённым acceptedTypes/acceptedCategories автора: при резервировании, реальной записи Storage и привязке к конкретному вопросу ответа. Настройка без ограничений остаётся без ограничений. Учитываются вложенные вопросы, valueName и динамические панели. MIME/расширения — декларативная проверка, не проверка сигнатур содержимого и не антивирус.
- Пороги frontend coverage: lines75/functions70/branches65/statements70. Добавлены поведенческие SQL, Edge, worker и реальные PostgREST HTTP-проверки.

## Применение

Пакет выпуска содержит три миграции. Для существующей БД применять только их, в порядке timestamp: 202611111200_counter_update_costs.sql, 202611111230_public_form_links.sql, 202611111300_upload_type_policy.sql. Не запускать supabase_schema.sql на рабочей БД.

Перед применением сохранить обычный резервный снимок и rollback-артефакты. На проверенном STSS владелец public.forms — postgres, storage.objects — supabase_storage_admin; supabase_admin имеет superuser. Миграции затрагивают обе схемы: выполнять с правами соответствующих владельцев/через существующую административную процедуру, не менять владельцев таблиц.

Нужно согласованно установить form-admin, frontend и новый mail-worker image (включая src/delivery.mjs). Миграции должны предшествовать использованию новых RPC клиентом. Старые открытые вкладки после отзыва anon SELECT/введения вопросных правил загрузки могут потребовать перезагрузки; старый frontend не является совместимым rollback после отзыва SELECT. Сохранение запрета перечисления важнее восстановления старого табличного API. Firewall/Nginx-конфиги для этого не меняются.

## Ограничения

Обычный SMTP и БД не образуют общей транзакции. При аварии процесса между SMTP и фиксацией результата или неопределённом SMTP-ответе дубли всё ещё возможны; исправлен конкретный повтор при ошибке DB ACK в работающем worker. Гарантия exactly-once не заявляется.

Строгий лимит ответов по-прежнему требует синхронизации записи. Пропускная способность перед дедлайном не измерялась, отдельная таблица счётчиков не вводилась. Наличие Basic-защиты Studio, отключённого GraphQL и закрытого anon OpenAPI не являлось подтверждённым обходом доступа; их конфигурация сохранена. Общие замечания о размере файлов и архитектуре сами по себе не стали основанием для массового рефакторинга.

PostgREST тесты используют настоящий HTTP-сервис и PostgreSQL; Auth/Storage инфраструктура SQL-фикстуры остаётся облегчённой. Полный Supabase end-to-end и реальная SMTP-доставка не заявляются.
