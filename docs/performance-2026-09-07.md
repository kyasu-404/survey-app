**Проверка производительности — 7 сентября 2026 года**

Исправлены четыре оставшихся пункта аудита. Сравнение выполнено относительно `c9396c1`
(включает предыдущие пять исправлений). Код и конфигурации подготовлены локально;
рабочие frontend, Edge Functions и Nginx не переключались.

Для карточек сохранён интерфейс «Показать ещё» и все открытые страницы. Новая страница
загружается отдельно. При обновлении перечитывается весь открытый диапазон, но порциями
до 999 карточек плюс lookahead; поэтому до 999 открытых карточек нужен один HTTP-запрос.
Объём данных остаётся пропорционален числу открытых карточек. Это сокращение числа запросов,
а не переход на получение только изменённых строк. Проверены вставка и удаление на границе
страниц, 1020 открытых карточек, ошибка второй порции и последующее восстановление.

В журнале рассылки UPDATE обновляет только письма выбранной рассылки. INSERT и неполный
DELETE также сверяют список рассылок. События объединяются за 500 мс с пределом ожидания
1 секунду; продолжающийся запрос сначала завершается. Панель обновляется при повторном
открытии и восстановлении подписки. Опрос раз в 5 секунд работает при отсутствии Realtime
и незавершённых письмах; при исправной подписке дополнительных опросов нет.

Настройка сборки теперь оставляет общие зависимости отдельно от отложенно загружаемых
библиотек. SurveyJS, конструктор и его стили не загружаются на входе; ExcelJS загружается
для выгрузки, Sentry — при наличии DSN. Новый контроль размера проверяет весь статический
граф начальной загрузки и не допускает возврата этих библиотек в него.

Браузерные замеры выполнены на локальных production-сборках, Chromium, сеть 10 Мбит/с с
задержкой 40 мс, замедление CPU в четыре раза, по три независимых контекста браузера на сборку.
Для обеих сборок использован одинаковый тестовый HTTP-сервер с gzip и кешированием: это
выделяет влияние разделения кода. Повторная загрузка каждой сборки передала 0 байт JS/CSS
из сети. Это лабораторное сравнение, а не замер скорости рабочих пользователей или отдельное
измерение выигрыша от кеширования текущего production. Картинки не входят в размеры JS/CSS.
Исходные результаты: [startup.json](performance-2026-09-07/startup.json).

В конфигурациях Nginx добавлено кеширование файлов с хешем на год, обязательная повторная
проверка HTML и 404 для отсутствующих assets. Защитные заголовки сохранены. Для общего IP
организации заданы API 100 запросов/с (burst 400), ответы 20/с (burst 200), запись файлов
10/с (burst 200); соединения frontend — 256. OPTIONS исключён из этих бюджетов, чтение файлов
не расходует бюджет записи. Ограничение по IP сохраняется; произвольный заголовок клиента
не позволяет обойти его. Новые имена зон допускают смену ключа при graceful reload.

На `magi` запущен отдельный временный Nginx только на loopback с тестовым upstream.
Серии по 200 OPTIONS, POST ответов, POST файлов и GET файлов, по 40 параллельных запросов,
завершились 200 успешными ответами каждая. Последующая серия из 400 POST получила
13 успешных ответов и 387 ответов 429: ограничение сохранилось. Проверен переход со старых
ключей зон через graceful reload, Cache-Control, ETag/304, HTML, 404 и защитные заголовки.
Исходные результаты: [nginx.json](performance-2026-09-07/nginx.json).
Тестовые POST передавали пустые тела обработчику-заглушке и не достигали рабочей базы,
Storage или SMTP. Этот тест проверяет поведение ограничений; он не подтверждает способность
backend одновременно принимать 200 больших файлов.

Также проверена полная конфигурация текущего `magi` с подставленными подготовленными vhost:
`nginx -t` успешен. Изменения относительно считанных файлов представлены в
[magi-nginx.patch](performance-2026-09-07/magi-nginx.patch); перед установкой нужно снова
считать актуальные vhost и использовать `ops/prepare-magi-nginx.py`, если они изменились.
Оба vhost устанавливаются вместе, с резервной копией и проверкой до reload. Для отката
восстанавливаются оба прежних файла. Предыдущие assets с хешами сохраняются для открытых вкладок.

Проверка рабочей БД на `stss` выполнена только чтением, со statement timeout 5 секунд.
В ней 9 форм и 5 ответов, расхождений счётчиков и ожидающих блокировок нет. По накопленной
`pg_stat_statements`: среднее время статистики главной 1,81 мс (максимум 5,04 мс),
наиболее частого списка форм 0,96 мс (максимум 1,82 мс), карточки формы 0,80 мс,
списка ответов 0,65 мс. Эти накопленные показатели не являются результатом нагрузочного теста.

Полный прогон frontend: 437 тестов в 61 файле; после добавления двух проверок явного offset
дополнительно прошёл весь файл API (25 тестов). Покрытие строк 76,51%, ветвей 68,32%.
Успешны TypeScript, ESLint, production-сборка, контроль размера, 80 проверок политик/серверного
кода и два сценария Playwright. Браузерный сценарий проверяет 200 карточек и их обновление
одним запросом, прокрутку 200 ответов, все строки скачанного XLSX, HTML, отчёт, пакетное
удаление, открытие публичной формы и настоящего конструктора без ошибок JavaScript.
Все данные в этом сценарии искусственные, запросы API перехвачены.

Повторение проверок:

```bash
cd frontend
npm run typecheck
npm run lint
npm run test:coverage
npm run build
npm run build:budget
node scripts/measure-startup.mjs /path/to/before/dist dist
npm run test:e2e -- e2e/responses.e2e.spec.ts
```

При проверке production-сборки через Playwright следует запускать `vite preview` и задавать
`E2E_BASE_URL` его локальным адресом. Для изолированной проверки Nginx используется
`python3 ops/check-nginx-performance.py /path/to/repository /usr/sbin/nginx`.

Документация, использованная при проверке: [группы кода Rolldown](https://rolldown.rs/reference/OutputOptions.codeSplitting),
[ограничения запросов Nginx](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html),
[проверка совместимости ключей зон при reload в исходниках Nginx](https://github.com/nginx/nginx/blob/master/src/http/modules/ngx_http_limit_req_module.c).
